# Module — Image editor

> **Scope change (decided 2026-11-17, see 4.4 and 8e):** the editor evolves from a Canva-like layout editor into a **Photoshop-like raster editor** (pixel layers, brush, selections, masks, blend modes, non-destructive adjustments, filters, history). This replaces the exclusion of pixel editing in 4.3 and in 8c.4. The phases are P0 to P11 in section 7b; each one updates the "Implementation status" when it is delivered.

> **Status: approved on 2026-11-16; phases 1, 2 and 3 delivered in code on 2026-11-17, not yet used in a browser, see "Implementation status".** Reverse engineering of Canva, the feasibility analysis and the specification of the design editor inside Aura Creative (menu "Designs"). The names of section 5 that phase 1 uses are in the registries ([../reference/](../reference/README.md)); the names of later phases (marked "later") are still proposals and may not be used in code before they are registered (GOLD-4). The import of all file formats is decided in section 8h and planned in [image-editor-import.md](image-editor-import.md). The sister document for video is [video-editor.md](video-editor.md), which reuses the presets, fonts, history and draft autosave of this module. UI copy is Brazilian Portuguese; everything else is English.

## 1. Goal and verdict

Let the team create and adapt post images (feed, carousel slide, story, cover) from a template, a brand's logo, colors and fonts, without leaving the platform, and send the exported image into the content flow (media library → content revision → approval → Instagram).

| Question | Answer |
|---|---|
| Can an editor **in the style of Canva** exist in this project? | **Yes, a focused one.** A layer-based editor (text, image, shape, background), templates, brand kit and PNG/JPEG export is feasible on the current stack. The browser does all the work, which is the same principle as ADR-14. |
| Can it be **Canva itself** (millions of templates, real-time collaboration, AI, print, presentations, whiteboard)? | **No.** Those are separate products with dedicated teams. Do not plan for them. |
| Does it fit the rules? | Yes, with **three documented decisions** to change first (section 3, items D1 to D3). Nothing here needs a weaker security rule. |
| Estimated size (one developer, estimate not a measurement) | MVP of section 4.1: about 6 to 9 weeks. Templates and brand kit: 2 to 3 weeks more. |

Recommended path: build the MVP of section 4.1 on a canvas library (Konva), store designs as versioned JSON, export through the existing media pipeline.

## 2. Reverse engineering of Canva

**Method and honesty.** Canva's source is closed. This section combines (a) what the product visibly does (public behavior), (b) what Canva has published (its engineering blog and job posts) and (c) **inferences** about the architecture. Each row says which one it is. Nothing here was verified against Canva's code.

Public sources: the Canva engineering post on [real-time mouse pointers](https://canva.dev/blog/engineering/realtime-mouse-pointers) (the editor uses websockets and Redis to propagate edits between people editing the same design, target of 3 pointer updates per second for up to 50 users on one design); the engineering post on [drawing in present mode](https://www.canva.dev/blog/engineering/draw-in-present-mode/) (the editor and the presenter are separate code domains); Canva job posts that name a dedicated "Lightspeed Renderer" team and an "Editing Foundations" team ([example](https://jobs.blackbird.vc/companies/canva/jobs/72657275-lightspeed-renderer-senior-software-engineer)). No public document describes the document model or the rendering pipeline.

### 2.2 Document model (inferred)

A design is almost certainly a tree: `design → pages → elements (with children for groups)`, each element with a type, a transform (x, y, width, height, rotation), z-order given by array position, and type-specific properties; assets are referenced by id, never embedded. Edits are small operations on that tree, which is what makes undo/redo, version history and real-time sync possible. This is the standard shape of every layer editor and is what section 5.2 proposes. **Inference, not evidence.**

### 2.3 Rendering (inferred)

Canva has a team called "Lightspeed Renderer", which implies a custom renderer tuned for speed rather than plain DOM. The practical lessons, whatever Canva uses inside: (1) the editing surface needs hardware-accelerated drawing for many layers; (2) text layout must be identical on screen and in export, so text is laid out by the app and not left to the browser's box model alone; (3) export must be deterministic: the same document gives the same pixels. Aura does not need to match Canva's performance: a page has tens of layers, not thousands.

### 2.4 Text

The hardest part of any design editor, and the first thing that breaks a naive build. Needs: font loading before measuring, wrapping at a box width, per-run styles (a bold word inside a sentence), alignment, line height, auto-grow of the box, and **the same result on export**. Canvas libraries draw text but have limited rich text. Proposal: one style per text element in the MVP (no mixed styles inside a box); mixed styles come later.

### 2.5 Export

Render the page at the target size and scale, encode PNG or JPEG. Done on the client in Canva's editor for simple cases and by servers for heavy cases (inference). For Aura the client export fits ADR-14 and avoids server CPU on Vercel.

### 2.6 What Canva has that Aura should **not** copy

Real-time collaboration, a stock catalog (licensing and cost), AI features, print workflows, presentations, whiteboards, an apps marketplace, a template marketplace. Each is a product by itself.

## 4. Scope

### 4.1 MVP (phases 1 and 2)

- Pages from presets (feed 1:1, 4:5, story/reel cover 9:16); a design has 1 to 10 pages, so one design is a whole carousel.
- Elements: text, image (from the media library through `MediaPicker`), rectangle, ellipse, line, group.
- Move, resize, rotate, snap guides, multi-select, layer order, lock, duplicate, delete, undo/redo.
- Text: curated fonts, size, weight, color, alignment, line height, one shadow.
- Image: crop inside a frame, flip, opacity, brightness and contrast, alternative text.
- Brand kit: the brand's logo, colors and fonts (from the brand's visual identity), chosen from a panel.
- Save as an immutable design version; restore a saved version into the draft; "Exportar" creates one PNG or JPEG media version per page and tells where to attach it to a content item.
- Autosave of the draft with optimistic locking (`version`).

### 4.2 Phase 3

Templates per brand ("Modelos"), "resize to another format" (a copy of the design in another preset). Still later, not planned: mixed text styles, filters beyond brightness and contrast, image background removal (needs a model, see section 6), comments on a design.

### 4.3 Out

Real-time collaboration, stock catalog, AI generation, print/PDF export, presentations, animation (video belongs to [video-editor.md](video-editor.md); an animated file imports its first frame, 8h). PDF page import (page 1 only; page selection in Phase 2) is decided in 8h and arrives in Phase 0. Pixel editing was listed as out by decision 8c.4; that decision is superseded by 4.4.

### 4.4 Photoshop-like scope (decided 2026-11-17)

In scope, delivered by the phases of section 7b: raster layers (pixels stored as PNG media), brush, eraser, eyedropper, fill and gradient; rectangular, elliptical, lasso and magic-wand selections with add/subtract/intersect, invert and feather; layer masks and clipping; all Canvas 2D blend modes plus fill opacity; adjustment layers (brightness/contrast, levels, curves, hue/saturation, color balance, black and white, invert, threshold); destructive filters (Gaussian blur, sharpen, noise, pixelate); clone stamp; free transform of a raster layer; layer groups as a tree; history with named steps and a pixel-patch budget; a Photoshop-style workspace (menu bar, tool groups with Photoshop's keys, options bar per tool, tab groups for Layers, Properties, Adjustments, History, Brand).

Still out (any addition goes through base.md 9.1): 16/32-bit editing, CMYK and color profiles in the editing pipeline (CMYK with ICC conversion on import enters scope in its own late phase since 2026-11-18, editing stays RGB 8-bit, 8h R5), Camera Raw, content-aware fill, 3D, actions and scripting, plugins, real-time collaboration on pixels, PSD and AI export, AI features. Import of PSD, AI and the other formats of 8h is in scope since 2026-11-18 (decisions 8g and 8h). Painting has no keyboard equivalent (UI-8): the accepted alternatives are fills, shapes, numeric selection entry and the layers list; this limitation is recorded here.

Technical limits (decided): page up to 4096 x 4096 px for raster documents, a resident raster memory budget of 512 MB, pixel history budget of 256 MB of tile patches, tiles of 256 x 256, desktop and tablet only (UI-7). The import limits of 8h.4 do not change these.

## 5. Technical design

### 5.1 Rendering library

| Option | Verdict |
|---|---|
| **Konva** (2D canvas scene graph, MIT) with `react-konva` | **Chosen.** Layers, transformer handles, hit testing, export to image and event model are built in; fits a layer editor and React 19 |
| Fabric.js (MIT) | Comparable; fewer React bindings; object model is mutable and imperative, which is harder to keep consistent with a versioned JSON |
| PixiJS (WebGL) | Faster for many sprites; heavier for text and editing handles; choose only if profiling shows Konva is too slow |
| Own renderer on `<canvas>` | Rejected: re-implements hit testing, transforms and text (CODE-12: do not add or build what a library already does) |

Versions in use: `konva` 10.9.1 and `react-konva` 19.3.2 (MIT). The canvas is loaded with `lazy()` in the browser only.

### 5.2 Document model

The design JSON is the source of truth, validated by zod on the server (SEC-6, `designDocumentSchema` in `lib/shared/design/schemas.ts`), with a closed set of element kinds (`DesignElementKind`, never loose strings). The canvas is a **projection** of the JSON: the editor state holds the document, Konva nodes are derived from it and every user action produces a new document. Undo/redo is a stack of whole documents (up to 100 steps); consecutive changes of the same field (typing, a slider, a drag of several elements) merge into one step. Assets are referenced by media version id, never by signed URL (DATA-15); the editor asks the server for fresh signed URLs (`useSignedUrls`, display copy for editing, original for the export).

Shape (version 2, decided 2026-11-17): `{ version: 2, pages: [{ id, background, elements[] }] }` with 1 to 10 pages. Version 1 (`{ version: 1, background, elements[] }`, one page, written on 2026-11-17 before this change) is still read: the reader turns it into a version 2 document with one page and the defaults below, the migration converts the drafts, and saved versions stay as they were (they are immutable). Only version 2 is written.

`background` is `#rrggbb` or `null` (a transparent page, shown on a checkerboard). Every element has `id`, `kind`, `x`, `y`, `width`, `height`, `rotation`, `opacity`, `locked` and `groupId` (`null`, or the same id on every member of a group); `x` and `y` are the top-left corner of the unrotated box and the rotation turns around the center of the box; the array order is the layer order (last on top). A **group** is the set of elements of one page that share a `groupId`: selecting one selects all, they move and resize together, and "Desagrupar" clears the id (the document stays a flat list, so every other operation is unchanged). By kind:

| Kind (`DesignElementKind`) | Own fields |
|---|---|
| `text` | `text` (up to 2000 characters), `font` (`DesignFont`), `fontSize` (8 to 400), `bold`, `italic`, `color`, `align` (`DesignTextAlign`), `lineHeight` (0.8 to 3), `shadow` (`null` or `{ color, blur 0 to 100, offsetX, offsetY -200 to 200 }`). One style per element. The height is not set by hand: the text wraps at `width` and the canvas writes back the measured height (without an undo step) |
| `image` | `mediaVersionId` (an image of the same brand), `flipX`, `flipY`, `zoom` (1 to 5), `focusX` and `focusY` (0 to 1), `brightness` (-0.5 to 0.5), `contrast` (-50 to 50), `alt` (up to 300 characters). The image always **covers** its frame: the frame is the crop, `zoom` enlarges the image inside it and the focus says which part stays visible |
| `rect` | `fill`, `cornerRadius` |
| `ellipse` | `fill` |
| `line` | `stroke`, `strokeWidth` (1 to 100), `dashed`. A straight line across the box at mid-height; rotate it for other angles |

Defaults when a field is missing (version 1 documents): `groupId` `null`, `shadow` `null`, `zoom` 1, focus 0.5, `brightness` and `contrast` 0, `alt` empty.

Colors inside a document are **user data** in the form `#rrggbb` (UI-9 is about the application's own interface); the defaults of a new element are read from the palette tokens at run time (`--ink`, `--surface`, `--violet`), and the brand kit offers the brand's own colors, so no color is written in the code. Limits: 10 pages, 100 elements in the whole document and 256 KiB (`design_too_large`). The page size is not in the document: it comes from the preset (`DesignPreset`): `feed_square` 1080×1080, `feed_portrait` 1080×1350, `story` 1080×1920.

Fonts (`DesignFont`), self-hosted from the `@fontsource` packages (SIL Open Font License 1.1, version 5.3.0, Latin subset, weights 400 and 700, normal and italic; Bebas Neue has only 400 normal), loaded on demand with the `FontFace` API under the family names "Design <name>", so the editor never depends on the `<link>` of the application: `dm_sans` "DM Sans", `cormorant` "Cormorant Garamond", `montserrat` "Montserrat", `playfair_display` "Playfair Display", `poppins` "Poppins", `lora` "Lora", `bebas_neue` "Bebas Neue", `inter` "Inter". Text is drawn after its font loads, on screen and in the export.

### 5.4 Flow

1. Create from a preset, from a template of the brand ("Modelo", phase 3) or as a copy of another design in another format ("Redimensionar", phase 3). The brand kit loads (logo, colors and fonts of the brand's visual identity).
2. Edit in the browser; draft autosave about 2 seconds after the last change with `version`; a conflict keeps the typed work and asks to reload.
3. **Export** ("Exportar": PNG or JPEG, 1x or 2x): the editor saves a version first, renders every page from the **original** files on an offscreen stage after the fonts load, encodes it, sends it through `sendUpload` (`requestUpload` → PUT → `confirmUpload`, exactly like any file; the server verifies content, size, quota) and records the link with `design_record_export`. A page exported again becomes a **new version of the same media asset** when the person has `media.update`; otherwise it becomes a new file. JPEG needs a background color on every page (a JPEG has no transparency). Images are read with `crossOrigin = "anonymous"`, so the private bucket needs the CORS `GET` rule of [../spaces/r2-storage.md](../spaces/r2-storage.md) section 6 (the same rule the upload already needs).
4. The exported media version is attached to a content item through the existing picker of the content editor. A content revision freezes the **media version**, not the design: later design edits never change an approved revision (GOLD-8).
5. "Versões" lists the saved versions; "Restaurar no rascunho" copies one into the draft (the draft changes, the saved versions never do).

### 5.7 Layout of the editor (decided 2026-11-17)

Reverse engineering of the workspace of desktop image editors (Photoshop, Affinity; public behavior only, from screenshots): a **vertical tool rail** on the left with exclusive tools and one-letter shortcuts, an **options bar** above the canvas that shows what the active tool or the selection can do, a **pasteboard** (a neutral area larger than the document) with zoom and pan, **docked panels** stacked on the right (transform, properties, layers) and a **status bar** with the size, the cursor position and the zoom. Only the structure is reused: no name, icon set, color scheme or wording of those products. Their pixel features (brushes, pixel selection, masks, adjustment layers, blend modes, Bézier pen) stay **out** (section 4.3): the editor stays a layout editor of section 5.2.

Layout (route with `staticData.fullScreen`, the same mechanism as the site preview: no admin sidebar, no `PageHeader`):

Tools and gestures:

- **Drawing:** with "Texto", "Retângulo", "Elipse" or "Linha", dragging on the canvas creates the element in that box (a line goes from the start point to the end point; Shift keeps a square, a circle or a 45° step); a click without dragging creates the default size centered on the click. ## 8e. Decisions (2026-11-17, Photoshop-like scope; the owner delegated them)

1. Pixel editing is in scope (4.4); 4.3 now lists only what is still out, and 8c.4 is superseded.
2. Engine: Konva stays the scene graph (handles, text, shapes); pixels live in an offscreen canvas per raster layer owned by a `RasterStore` outside React state; composition uses Canvas 2D blend modes; heavy operations run in a Worker with OffscreenCanvas. **No PixiJS, WebGL or wasm now** (CODE-12); WebGL is reconsidered only if a measured slider drag on a 4096 page exceeds 150 ms.
3. Pixels are one PNG per raster layer (and per mask, 8-bit grayscale) in the media library, referenced by `mediaVersionId`; the document JSON keeps its 256 KiB cap. Flushes are idle-based (8 to 10 s), on "Salvar versão", on export and on leaving; the JSON references a file only after `confirmUpload`. Layer files are hidden from the library listing by a flag and counted in `media_usages`.
4. Document version 3 keeps a **flat** element array; layer groups use `parentId` (a tree by reference), `groupId` stays the selection group. `maxElements` rises from 100 to 200.
5. Non-destructive adjustments are layers with validated parameters, evaluated by a pure pipeline (testable without a DOM); filters are destructive on a raster layer.
6. History for pixels is a patch of 256 x 256 tiles (before and after), outside the JSON history; document-only steps stay references; steps are named (pt-BR) for the History panel.
7. Selections are session-only 8-bit masks, not part of the document.
8. Photoshop's single keys are adopted (V M L W C I B S E G T U H Z X D, `[` `]`); the old layout keys move: shape tools under U, image import Ctrl+Shift+K; Ctrl+D deselects when a pixel selection exists and duplicates otherwise; Ctrl+J duplicates a layer. Keys are ignored while a text field has focus; every command also has a menu item.
9. The workspace stays light with the existing tokens until the workspace token set of `color-palette.md` is measured; a scoped dark workspace is a later, separate decision.
10. No new action is needed: `design.update` gates every tool and `media.upload` the flush, as for export. No dependency is added now; `ag-psd`, `wasm-vips`, OpenCV.js and `lazy-brush` are candidates that need their own reason and license check (CODE-12).
11. Migrations of P4 are written and tested locally only. Pushing them to the linked production project needs the owner's explicit go-ahead.
12. References studied (public behavior and licenses checked on 2026-11-17, not code copied): miniPaint (MIT), Klecks (MIT), filerobot-image-editor (MIT), Konva (MIT), pixijs/filters and glfx.js (MIT, shaders to read), Pinta (MIT, algorithms). Not usable as dependencies: Drawpile (GPL-3.0), Polotno and Pintura (commercial), tui.image-editor (archived). Photopea is proprietary: behavior only.

## 8f. Decisions (2026-11-18, re-cut after the audit)

1. The order of the phases is P6 to P11 as in 7b.
2. Hidden pixel files: flush on save, version, export and a 60 s idle (not 8 s); the purge policy and `design.update` versioning of hidden assets are implemented as a new migration (local first). This supersedes the 8 to 10 s idle in 8e item 3.
3. The screen/export z-order and the unified timeline are fixed (P6) before new features.
4. Adjustment layers and masks enter the UI earlier (P8, P10) because the pipeline already supports them.
5. Layer styles, text extras, shape stroke, pen tool and PSD import stay separate later decisions. PSD needs `ag-psd` (MIT, 34.2.1 verified on npm) with a transitive license check (CODE-12). Superseded in part by 8g and 8h.
6. `getMedia` does not filter hidden assets, by design: `hidden` is a display flag of `listMedia`, not a permission (RLS unchanged).

## 8g. Decisions (2026-11-18, PSD and AI import, requested by the owner)

1. "Arquivo > Importar PSD ou AI…" (renamed "Importar…" by 8h.1) adds the file to the current page; no new server function, route, table, action or error code (client-side only, GOLD-2: it reuses raster layers, the `RasterStore`, the hidden-pixel flush and `media.upload` gate of paste). If the page has no element the page takes the file's size (64 to 4096, as crop does); otherwise the layers are placed at 0,0 and the page keeps its size. One history step "Importar PSD" or "Importar AI".
2. PSD: `ag-psd` 34.2.1 (MIT; transitive `pako` MIT and `base64-js` MIT), loaded with `import()` only when a PSD is chosen, read with `useImageData` (no canvas needed). Layers become raster layers (name, order, `hidden`, `opacity`, `fillOpacity`, position, blend mode where an equivalent exists), PSD groups become `group` elements through `parentId` (depth up to 8, deeper groups are flattened), clipping becomes `clipToBelow` only above a pixel layer, an enabled layer mask is baked into the alpha. Text, smart objects and shape layers arrive as the pixels Photoshop stored (text is not editable). Layer styles, adjustment layers, vector masks, linked/embedded smart-object editing, fonts are not imported; CMYK, grayscale and indexed are converted by `ag-psd` without a profile; 16/32-bit is reduced to 8-bit. Multichannel, duotone, Lab and PSB are refused.
3. AI: only files that carry a PDF stream (modern `.ai`, or `%!PS-Adobe` files with an embedded `%PDF-`); `pdfjs-dist` 6.5.438 (Apache-2.0), loaded with `import()` only for AI, worker as a Vite `?url` asset. The first artboard is rasterized at 2x (capped at 4096 px, transparent background) into one raster layer named after the file; vector data and Illustrator layers are not kept. A legacy file without PDF compatibility is refused with the message that explains how to re-save it. Password-protected files are refused.
4. Validation: the file type is decided by content (`8BPS` with version 1 for PSD; `%PDF-` in the first 1024 bytes or `%!PS-Adobe` for AI) and the extension must agree; up to 100 MB; PSD header is read before decoding (canvas up to 4096 x 4096); total pixel memory against the 512 MiB raster budget and the 200-element limit are checked before anything is added. Failures are `invalid` results (`Result` and `invalid`), never thrown; the messages are in the glossary. The imported pixels follow the normal hidden-pixel flush, so the import needs `design.update` and `media.upload` and counts toward the 300 live hidden versions per user and brand (a PSD with many layers can hit `hidden_limit_reached`).

- Raster paint gating: recommend gating paint tools on `Media.Upload` in addition to `design.update`.
- Hidden asset sharing and publishing: recommend forbidding both (hidden assets are internal to the design).

### 8h.4 Limits and hardening

- Unchanged from 4.4: page 64 to 4096 px per side, 200 elements per page, raster budget 512 MiB, group depth 8, layer name 80 characters.
- A PSD layer is refused when its side is above 16384 px or its decoded bytes do not fit the remaining raster budget; a layer larger than the page but within these limits is cropped to the page. A PSD with more visible leaf layers than the page can take is refused before any decode.
- Time limits: 60 s for PSD and images, 30 s for the PDF render; on expiry the worker is terminated or the pdf.js task is destroyed. The user can cancel an import.
- `DESIGN_IMPORT_LIMITS` (`src/lib/shared/design/import/limits.ts`) holds `maxPageSide` (4096), `minPageSide` (64), `maxLayerSide` (16384), `workerTimeoutMs` (60 s, PSD and images), `pdfTimeoutMs` (30 s, PDF render), `pdfHeaderWindowBytes` (1024), `jpegHeaderWindowBytes` (256 KiB), `aiTargetScale` (2) and `aiMaxImagePixels` (16 777 216). Per-format `maxBytes` lives in each handler.
- PSD decoding runs in a worker; the main thread validates every worker response again (buffer length equals width times height times 4, limits, total budget). Without `Worker` support the PSD import is refused. The worker is a responsiveness boundary, not a security boundary (R6).
- PSD uses two passes (checked against ag-psd 34.2.1). Pass 1: `readPsd(buf, { useRawData: true, useRawThumbnail: true, skipCompositeImageData: true, skipThumbnail: true, skipLinkedFilesData: true, imageResourcesWhitelist: [] })`, then an iterative walk of the layer tree (no recursion) that computes, with overflow-safe arithmetic, the count, side and bytes of every layer, including mask rectangles, bit depth and channel count (CMYK = 5 channels), with budget checks before any pixel exists. Pass 2: `getLayerImageData` / `getLayerMaskImageData` one layer at a time, dropping each `PixelData` before the next. The worker calls `initializeCanvas` with a non-canvas `createImageData`. `getLayer*ImageData` has no memory cap, so the pass-1 arithmetic is the only brake; the exact error `Exceeded memory limit` maps to the memory-budget message. The whole-file `readPsd` with `totalMemoryLimit` was a documented fallback that was not needed; it does not exist in the code (Phase 0 deviation 3).
- A header not found or not parsed within its window is refused. The `%PDF-` marker counts when it starts before byte 1024 (accepted at 0, 900 and 1023; refused at 1500). After decoding, the actual size must equal the declared size or the result is discarded.
- Images: the declared dimensions are read from the header bytes and checked against the raster budget before decoding. JPEG headers are searched in the first 256 KiB; the PDF header is searched in the first 1024 bytes.
- pdf.js (`pdfjs-dist` 6.5.438; at least 4.2.67 is required for CVE-2024-4367; spike of 2026-11-18): the bytes are passed as data only, never as a url; `disableAutoFetch`, `disableStream`, `disableRange` and `enableXfa: false`; `useWorkerFetch` false or unset; no `cMapUrl`, `standardFontDataUrl` or other URL option (non-embedded fonts fall back); `maxImageSize` equals `aiMaxImagePixels`; a bundled same-origin `workerSrc`; canvas-only rendering (no text, annotation, XFA or form layer); the planned canvas bytes are checked before the canvas is created; `stopAtErrors` is `false` (render what can be read, a damaged page still shows as pixels). The installed version has no `isEvalSupported` and no `enableScripting` option in `getDocument`; scripting is inert because only `page.render` to a canvas runs, so neither option is used. One helper, `import/render-pdf-page.ts`, builds the options (pure `buildPdfOpenOptions`) and renders page 1 for both `ai.ts` and `pdf.ts` (Phase 0 item 0-7). Before the canvas exists it checks that the first-page viewport is finite and above 0, that no side is above `maxLayerSide`, that the render size fits the page limits, and that the canvas bytes plus the store's used bytes fit the raster budget; the render is raced against `pdfTimeoutMs`; the task is destroyed and the canvas released (0 x 0) in every case.
- Sketch and ZIP limits (Phase 4; owner decision 2026-11-18: accept plan recommendations; single source, the plan points here; code: `SKETCH_LIMITS` in `src/lib/shared/design/import/limits.ts`): file 100 MiB; entries 2000; total inflated bytes 256 MiB; per entry inflated cap 32 MiB for `pages/*.json`, 4 MiB for `document.json` and `meta.json`, 64 MiB for an image; ratio 200:1 per entry once the output is above 1 MiB; end-of-central-directory search window 64 KiB (plus the 22 byte record); entry name 255 characters; JSON nesting 128 levels (checked by a scan of the text before `JSON.parse`) and 2 000 000 values per file; artboards listed 100; group depth 8 (`DESIGN_LIMITS.maxGroupDepth`); symbol resolution depth 1; image pixels 64 Mpx each (and the raster budget check of R10 before allocation: the FULL declared decode, width times height times 4, is charged against the remaining budget before any decode, not only the downscaled target); bitmap decodes per job 32 and one decode per image reference and flip (later layers copy the first result); a decoded size equal to the requested target is NOT a check (`createImageBitmap` always returns the target size), the real check is that the buffer length equals width times height times 4; timeout 30 s; meta `version` at least 88 (Proposed, unverified: no real `.sketch` file is available, P-4.3 blocked). The reader is our own bounded central-directory reader with `DecompressionStream("deflate-raw")` (decision D4-4 deviation: no `fflate`, no new dependency, no stack row; the compressed bytes are fed in 16 KiB slices by a pull-based stream and the running output counter, the ratio against the bytes fed and the declared size are checked between reads, so one slice can add at most about 16 MiB; whether browsers inflate slice by slice and honor backpressure is NOT proven, only Node); the archive is refused as a whole when any entry name is unsafe (`..` or `.` segment, leading `/` or `\`, drive letter, NUL, backslash, empty, over 255 characters, duplicate or case-variant duplicate), when it has more entries than the cap, when the encrypted flag, zip64 fields, several disks or overlapping entries appear, when the end record is not the last bytes of the file, or when a local header name differs from the central directory name. Only `document.json`, `meta.json`, `pages/*.json` and the `images/*` entries a layer references by exact name are ever inflated; every inflate is bounded by a running byte counter that does not trust the declared sizes, and the actual size must equal the declared size. Rendering is bounded by the raster budget before each layer, by a cost cap of `maxRenderCost` (1 000 000 000 units, summed per artboard: pixels times polygon edges times the 16 coverage subsamples for shapes, plain pixels for text and bitmaps; shapes are rasterized at their unscaled frame geometry into a buffer clamped to the artboard side and to 4096 px and are placed at frame times scale, they are NOT clipped to the artboard and the pixels are NOT scaled: fidelity limit, not a security limit) and by a 30 s deadline checked between layers inside the worker. Memory of the JSON side: repeated page references in `document.json` are deduplicated; one cap of 8 000 000 JSON values for the whole job (meta, document and every page read, the 2 000 000 per file cap stays); the artboard probe keeps only the artboard list and drops every parsed page; the build job parses only the page of the chosen artboard (a file with one artboard re-reads that page, counted in the same cap). Layer names are cut by code points to 80 UTF-16 units, so no lone surrogate is produced. The request schema also refuses a file above 100 MiB. All Sketch parsing runs in a dedicated Sketch worker (`worker/sketch.worker.ts`, `sketch-protocol.ts`, `sketch-engine.ts`, `sketch-client.ts`): central directory, bounded inflate, `JSON.parse`, schema validation, node-to-layer mapping, shape rasterization, text painting and bitmap decoding (`OffscreenCanvas` and `createImageBitmap`, worker-capable; the DOM-free fallback is to skip the node and count it as `unsupported_node`). Nothing of Sketch parsing stays on the main thread; the main thread only builds the elements from the validated response. One job at a time per worker; the client terminates the worker on the 30 s timeout, on cancel and after every response, refuses when `Worker` does not exist, and re-validates every response with zod (`byteLength` equals width times height times 4 per layer, page and layer sides against the limits, layer count against the capacity, total against the raster budget of R10); the artboard choice is a probe job that returns the options, and the chosen index starts a second job that parses the file again. Proven by unit tests (Node): dedupe of 40 refs to a 1M-value page, the job value cap with 5 distinct heavy pages, probe and resume by page, the declared-decode budget refusal with zero decodes, the decode cache and cap, name cutting, the clamped image-too-large refusal and the file size refusal. NOT proven without a browser: real peak memory of `JSON.parse` and `createImageBitmap`, OOM behavior, decode memory with the resize options. A hung worker is terminated, so a single synchronous rasterization is now interruptible by the timeout.
- Logs and toasts never carry file names with personal data, file bytes or file text (SEC-12). `logError` receives a fixed context label and the error name or class, never the message of an error raised while parsing file content.
- Phase 0 security fixes (2026-11-18): the planner checks one combined peak per layer (decoded layer pixels plus the crop buffer plus the decoded mask, and for the composite its converted copy) against the remaining budget, and the decoder releases the layer pixels before the mask is decoded. When every layer decodes to nothing and the file has a composite, the worker reads the structure a second time with `skipCompositeImageData: false` (ag-psd keeps `rawCompositeData` only then), re-plans with the same budget check and imports the flattened image. Names are cut by code points only (the sanitizer also removes every `Cf`, `Zl`, `Zp` and `Co` character and tag characters). pdf.js runs with `verbosity: 0`. The main thread refuses a worker response in which one `ArrayBuffer` backs two layers or a buffer is resizable.

- SVG (Phase 3a, R1, D3-5): refuse, never rewrite. The only rewrite is adding `width` and `height` to the root of an already gated tree when the file has no usable pixel size; the result is gated again. Caps: file 5 MiB (checked by `file.size` before reading), 5000 elements, 50 `use`, depth 64, 100 000 characters in one `style` value or `style` element, 67 108 864 declared pixels in total over ALL embedded `data:image` URIs (sum, not per image); a duplicate `id` or `xml:id` is refused (a browser resolves `#a` to the first element, the gate must not see another), a `use` with more than one `href`-like attribute (`href`, `xlink:href`) is refused (browsers pick one by precedence), a `#fragment` is percent-decoded like the browser before the lookup, and a DOCTYPE with `SYSTEM` or `PUBLIC` is refused (only a bare `<!DOCTYPE svg>` passes); UTF-8 only (a NUL byte or invalid UTF-8 is refused), render timeout 10 s. The threat model is in [image-editor-import.md](image-editor-import.md) section 3.8a.

### 8h.5 Metadata (Phase 1)

- `ImportedDesign.metadata` is a validated, size-capped object produced deterministically from the file (version, source format and color mode, dimensions, layers, text runs, fonts, declared colors), with no model call. The strict schema is validated on the client and again on the server.
- Caps: 1000 layers, layer name 200 characters, text run 5000 characters, 100 000 characters of text in total, 100 fonts, 64 colors, 1 MiB for the whole JSON. On overflow the lists are truncated, the `truncation` flags are set and the import note `metadata_truncated` is emitted (kept; registered in Phase 1 item 1-1 with `DesignImportColorMode`: `grayscale`, `rgb`, `cmyk`, `indexed`, `bitmap`, `unknown`).
- Fields and caps (code: `src/lib/shared/design/import/metadata.ts`, `importedDesignMetadataSchema`, `ImportedDesignMetadata`, `METADATA_LIMITS`; every object is strict, so an unknown field is refused). `DesignImportColorMode` is the registry enum; layer `kind` and color `source` are local closed unions.

| Field | Content | Cap |
|---|---|---|
| `version` | integer, 1 | fixed |
| `source` | `format` (`DesignImportFormat`), `colorMode` (`DesignImportColorMode`: `rgb` for decoded images, `unknown` for PDF and AI), `bitsPerChannel` (integer or null), `pageCount` (integer or null; only PDF and AI) | none |
| `dimensions` | `sourceWidth`, `sourceHeight` (the file), `pageWidth`, `pageHeight` (after clamp or downscale) | integers 1 to 300 000 |
| `layers[]` | `index`, `parentIndex` (null or smaller than `index`), `name`, `kind`, `visible`, `opacity` (0 to 1), `blendMode` (source name), `bounds` (`left`, `top`, `width`, `height`, or null for a group) | 1000 layers; name 200 characters; blend mode 40 characters |
| `textRuns[]` | `layerIndex`, `text`, `fontName` (or null), `fontSize` (or null), `color` (`r`, `g`, `b` integers or null; no hex strings). PSD only; one run per text layer | 1000 runs; 5000 characters a run; 100 000 characters in total |
| `fonts[]` | `name`, `usageCount` (style runs that use it) | 100 fonts; name 200 characters |
| `colors[]` | `r`, `g`, `b`, `source`, `count` | 64 colors |
| `truncation` | `layers`, `textRuns`, `fonts`, `colors` (booleans) and `textCharsDropped` (characters not stored because of a cap; stripped control characters do not count) | none |
| whole object | `JSON.stringify` size in UTF-8 bytes | 960 KiB (1 MiB minus a 64 KiB margin, `METADATA_LIMITS.jsonBytes`); the build drops `textRuns` first, then the metadata is dropped (null) |

- Size, one definition per layer (Phase 1 hardening): the database measures `octet_length(metadata::text)` against 1 048 576 bytes (`METADATA_LIMITS.storedJsonBytes`); `jsonb` text output adds a space after every `:` and `,`, so it is larger than `JSON.stringify`. The zod cap is lower by `METADATA_LIMITS.jsonTextMargin` (64 KiB, more than the separators of 1000 layers, 100 fonts and 64 colors), so a payload that passes zod is never refused by the database for size. A test builds a payload of exactly the zod cap (accepted) and one byte more (refused).
- Database shape check (Phase 1 hardening, migration `20261119110000_design_import_metadata_hardening.sql`): `design_record_import` is callable directly by any `design.update` user, so it validates the shape itself and answers `invalid_input` (a non-array or non-object at any level never reaches `jsonb_array_length`): only the keys `version`, `source`, `dimensions`, `layers`, `textRuns`, `fonts`, `colors`, `truncation`, all required; `source.format` in the closed list of `DesignImportFormat` (all 14 values since migration `20261119120000_design_import_metadata_formats.sql`: `psd`, `ai`, `pdf`, `png`, `jpeg`, `webp`, `tiff`, `avif`, `gif`, `ase`, `aco`, `gpl`, `svg`, `sketch`; the palette formats `aco`, `ase`, `gpl` never produce metadata and are listed only because `check:consistency` pairs every `DesignImportFormat` value with the `check in (...)` on `source_format`); `source.colorMode` in the `DesignImportColorMode` values; layers at most 1000 with exactly the 8 keys, `name` at most 200 and `blendMode` at most 40 characters without control, format or bidi characters, `kind` in the closed union; `textRuns` empty; fonts at most 100 (name at most 200 characters, same character rule); colors at most 64 with integer channels 0 to 255 and `source` in `text`, `fill`, `swatch`; `truncation` with its 5 keys. The server schema (`storedDesignMetadataSchema`, used by `recordDesignImportSchema`) refuses non-empty `textRuns` instead of overwriting them, and the client empties the runs with `withoutText` (`metadata.ts`), which also sets `truncation.textRuns` and adds the dropped characters to `textCharsDropped`.
- Rows per design (Phase 1 hardening): the function keeps the latest 20 rows of a design and deletes older ones in the same transaction (the table has no update or delete policy, so only the `security definer` function prunes; no new error code). Audit events are not pruned.
- Source file names are not stored in the metadata (SEC-12): there is no `fileName` or `source_name` field in the object or in the table. The layer name of an imported file comes from the file name, goes through the sanitizer and lives only in the design.
- Layer `kind` values: `raster`, `group`, `text`, `smart_object`, `adjustment`, `shape`, `unknown`. Color `source` values: `text`, `fill`, `swatch`.
- Strings go through one sanitizer (filter control, bidi-override and zero-width characters, then NFC, then truncation on code points, then trim; idempotent: sanitizing twice gives the same result). Layer `kind` is a closed union local to the metadata, not an enum row.
- Text strings are stored only for a named consumer. Until a consumer exists, text runs are not persisted (layer names and fonts only). No EXIF, GPS, XMP, IPTC, ICC, comment or text chunks, PSD image resources, embedded thumbnails, document title or author, file path or file-system data is stored (SEC-12). The table has RLS: read by `has_action('design.view')` plus `can_access_brand(brand_id)`, never through `portal_*`; writes only through the server function; rows are deleted with their design (`ON DELETE CASCADE`); `created_by` has no `on delete` action, so a profile deletion is blocked, not cascaded. "No purge path" means no separate retention job (GOLD-8).
- Names that come from files or file names go through the sanitizer above before they enter the document.
- Colors come only from declared values, not from pixels.
- Consumers must treat every string as untrusted data and never as an instruction. Any use by a model provider is a separate decision and is not built.
- A metadata failure never fails the import. The table `design_import_metadata`, the function `design_record_import`, the server function `recordDesignImport`, the audit action `design.import_recorded` and the error `design_import_metadata_too_large` are registered in [../reference/](../reference/README.md) (migration `20261119100000_design_import_metadata.sql`, local only). The function refuses a non-empty `textRuns` (and any shape outside 8h.5, migration `20261119110000_design_import_metadata_hardening.sql`), so text runs cannot be persisted until a named consumer changes it through the documents first.

1. Layer files are media assets with `hidden = true` (scope brand, created through `requestUpload` with `hidden`; needs `design.update` in the database). Hidden assets never appear in `listMedia` (library, picker, search); they stay visible to the storage summary and are protected from deletion by `media_usages`.
2. The draft JSON references a `pixelsVersionId` only after `confirmUpload` succeeded; the patch is applied to the whole history (past, present, future) without a visible undo step, and the dirty flag is cleared only if no stroke arrived during the upload.
3. Flush triggers (P6a): 60 s without strokes (`DESIGN_LIMITS.pixelFlushMs`; the idle flush skips a layer sent less than 15 s ago, `pixelFlushMinGapMs`), "Salvar versão" and export (both flush first and stop if the flush fails), and the unsaved-changes guard while pixels are dirty or uploading. Without `media.upload` the paint tools are disabled, so the flush is never scheduled and nothing blocks leaving. Flushes are serialized and retried once per layer; one round applies all new `pixelsVersionId` values in a single history update.
4. Version ownership: the first flush of a layer creates a new hidden asset; later flushes in the same session add a version to that asset only when the user has `media.update`, otherwise (or if that fails) a new hidden asset is created.
5. A duplicated raster layer loads its own copy of the pixels and is marked dirty, so it flushes to its own file.
