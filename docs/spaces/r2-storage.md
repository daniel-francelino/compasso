# File storage — Cloudflare R2

> How Compasso stores and serves files: Cloudflare R2 behind a storage interface, two buckets (private originals and public derivatives), direct browser upload through presigned URLs, and server-side authorization of every signature. It serves the [media library](media-library.md). The interface and the security rules come from the Memoria Print project (where the same layer was written for R2 using `aws4fetch`). Pricing and limits of Cloudflare change: confirm them in the official pages before deciding. UI messages are Brazilian Portuguese; everything else is English.

## 1. Why R2

The library keeps originals, reduced copies of every image and videos or PDFs shown to clients. R2 has a generous free tier, an S3-compatible API and **does not charge for egress traffic**, which matters when clients open the same approval files many times. The database and authentication stay in Supabase: only the binaries live in R2. Files never pass through Vercel functions (their request body is limited to about 4.5 MB): the browser talks to R2 directly with signed URLs.

## 2. Storage layer

All the code goes through the interface in `src/lib/shared/storage/types.ts`; only `r2-storage.server.ts` knows the provider, `server-storage.server.ts` is the single place that builds it (and returns `null`, shown as `storage_unavailable`, when the R2 variables are missing) and `browser-storage.ts` is the browser side. Pages and components never know the provider.

| Interface | R2 implementation |
|---|---|
| `createUploadTarget(path)` | Presigned **`PUT`** URL (SigV4, about 10 minutes, bound to one object key; `aws4fetch` cannot bind `Content-Type`, so type and size are validated by `confirmUpload`, section 5). Returned as `{ path, url }` |
| `BrowserStorage.upload(target, body, contentType)` | `fetch(target.url, { method: "PUT", body, headers: { "Content-Type": contentType } })`; success if the answer is 2xx |
| `signUrls(paths, seconds, downloadName)` | Presigned `GET` URLs computed **locally** (no network call); `downloadName` goes in `response-content-disposition` |
| `stat(path)` | `HEAD`: size and content type |
| `readRange(path, range)` | `GET` with `Range` |
| `download(path)` | Authenticated `GET` → `Blob` |
| `remove(paths)` | `DELETE` per object, in parallel (or `DeleteObjects` in batches) |

Implementation: **S3 API over HTTP with `aws4fetch`** (signs requests with SigV4; small; runs on Node, which is what Vercel functions use). A Worker *binding* is not an option on Vercel.

### 2.1 Object keys

Opaque and generated by the server, never derived from user input: `<uuid>` (original), `<uuid>-thumb`, `<uuid>-display`. No client names, no original file names (kept only in the database, `media_versions.original_filename`), and the key is **never** used as access control. No signed URL is stored anywhere.

## 3. Buckets and secrets

| Bucket | Content | Access |
|---|---|---|
| `R2_BUCKET` (private) | Originals, thumbnails, display copies, PDFs, evidence files | Only the S3 API with server credentials; reads through short signed URLs |
| `R2_PUBLIC_BUCKET` | **Derivatives explicitly published** for the public site | Custom domain `SITE_MEDIA_BASE_URL` with Cloudflare cache; never connect a public domain or `r2.dev` to the private bucket |

**Server-only** variables (never with the `VITE_` prefix): `R2_ACCOUNT_ID`, `R2_ENDPOINT` (use the jurisdiction endpoint if the bucket has one, for example `https://<account>.eu.r2.cloudflarestorage.com`), `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` (a token restricted to **these two buckets** and "Object Read & Write"), `R2_BUCKET`, `R2_PUBLIC_BUCKET`, `SITE_MEDIA_BASE_URL`. They live in the Vercel project settings (production and preview with different buckets).

S3 address: `https://<R2_ACCOUNT_ID>.r2.cloudflarestorage.com/<bucket>/<key>`.

## 4. Security moves into the code

R2 has no per-user policies: the server signs with **application credentials** that can do anything in the bucket. Authorization is therefore solely the server's.

Rules that apply at every point:

1. **Sign only keys read from the database with the person's session** (so already filtered by RLS), never keys sent by the browser. Asking for an arbitrary key by ID returns nothing.
2. Before signing a read, check **at that moment**: internal user with `media.view` and brand access (or `site.view` for site media); external user with `portal.view`, a brand link and a shared revision that references that exact version.
3. `createUploadTarget` only after the upload session exists, and the session creation checks `media.upload` and the brand.
4. `remove` only for records the person may delete, and never for files referenced by approved revisions.
5. Signed URLs are short: **5 minutes** for internal users, **2 minutes** for external users. A signed URL already issued remains valid until it expires, even if access is revoked afterwards; this is accepted and documented.

## 5. Limits the bucket does not enforce

A presigned `PUT` does not fix type or size. Compensation, all on the server (`confirmUpload`):

- **Measure before reading:** `stat(path)`; refuse without reading if the size differs from the declared one. This protects function memory.
- **Verify the real content** with the first bytes (and, for PDF, the start `%PDF-` and the end `%%EOF` through a `Range` request); the declared MIME type and extension are not trusted.
- **Reduced copies** (thumbnail and display, generated in the browser by redrawing to a canvas): each must be an image under a cap (2 MiB), otherwise the session is discarded and the objects deleted.
- **Checksum:** SHA-256 of the original, computed from the bytes read.
- Upload sessions that are never confirmed expire after **24 hours**; a daily Vercel Cron route deletes them (and their objects) and reconciles objects without a database record using a 48-hour margin.
- **Quota:** `media_storage_used()` adds originals, reduced copies and pending sessions; uploads are refused with a clear message when the quota would be exceeded (existing files are never deleted automatically).

## 6. Browser CORS

The browser sends directly to R2, so the private bucket needs a CORS rule:

- `AllowedOrigins`: the production domain, the preview domain(s) and `http://localhost:<dev port>` (the exact port of the dev server).
- `AllowedMethods`: `GET`, `PUT`, `HEAD`.
- `AllowedHeaders`: `Content-Type`.
- `ExposeHeaders`: `ETag`, `Content-Length`.

```json
[
  {
    "AllowedOrigins": ["http://localhost:8080", "https://app.your-domain.example"],
    "AllowedMethods": ["GET", "PUT", "HEAD"],
    "AllowedHeaders": ["Content-Type"],
    "ExposeHeaders": ["ETag", "Content-Length"],
    "MaxAgeSeconds": 3600
  }
]
```

Without it the browser blocks the upload with a "CORS error" before the request reaches R2, and the UI shows "Não foi possível enviar o arquivo". PDF preview in an `iframe` and thumbnails in `<img>` need no CORS. The public bucket needs none either (read through `<img>`).

## 7. Public space of the site

The CMS publishes web copies of the images the site uses (see [public-site-delivery.md](public-site-delivery.md)). Setup:

1. Create the public bucket (for example `compasso-site`) in the same account.
2. Give the S3 token "Object Read & Write" access to this bucket too.
3. In Settings → Custom Domains, attach a domain (for example `media.your-domain.example`). Do not use `r2.dev` in production.
4. Configure `R2_PUBLIC_BUCKET` and `SITE_MEDIA_BASE_URL` (`https://…`, no trailing slash).

Files are named by the content hash (`site/<hash>-400.webp`, `-1600.webp`) with `Cache-Control: public, max-age=31536000, immutable`. Publishing is an explicit action (`media.publish`); withdrawing deletes from the public bucket and purges the Cloudflare cache. **The original is never copied.**

Performance note: presigned URLs change on every request, so the browser does not cache them; optionally round the expiry to fixed blocks (for example to the minute) so the same URL repeats briefly. Images behind signed URLs are rendered `unoptimized` (no image optimizer in the middle).

## 8. Backup and retention

- R2 objects have no automatic cross-bucket backup: define a policy (replication to a separate bucket or object lock, according to need) and **test restoring** every quarter, together with the PostgreSQL restore test.
- The media trash keeps files for 30 days (configurable); permanent deletion only without references.

## 9. Acceptance criteria

- [ ] JPEG, PNG, WebP, MP4 and PDF can be uploaded within the limits; thumbnails and previews appear; the record downloads the original with the right name.
- [ ] A file above the declared size, or with fake content, is refused **without being downloaded in full** and the object is deleted.
- [ ] Whoever lacks `media.view` (or the portal link for the revision) gets no URL; asking for an arbitrary key by ID returns nothing.
- [ ] An expired URL stops working; the upload URL cannot be used to read or delete.
- [ ] The private bucket cannot be read directly from the internet; no R2 secret appears in browser code or server responses.
- [ ] A file used by an approved revision cannot be overwritten or permanently deleted.
- [ ] Incomplete uploads and orphan objects are cleaned by the daily job.

## 10. Required validation (before production)

With a rehearsal bucket: the presigned `PUT` from the browser, the `GET` signature with `response-content-disposition`, `HEAD` and `Range`, CORS with the real domains, and the refusal for lack of permissions described above. Memory of the function while confirming a 50 MiB PDF (the checksum needs all the bytes) on the real Vercel plan.

## 11. Open decisions

| Decision | Proposal |
|---|---|
| Video size in the MVP | Up to 100 MiB; multipart upload in phase 2 |
| Caps of the reduced copies | 2 MiB each, reviewed with real sizes |
| Count reduced copies in the quota | Yes |
| Backup of R2 | Replication or object lock; decide with the retention policy |
| Signed URL lifetimes | 5 min internal / 2 min external; revisit if clients complain |
